# Security Policy

## Reporting a vulnerability

Report security issues privately through GitHub's [private vulnerability reporting](https://github.com/NoahHakansson/sk64/security/advisories/new) rather than a public issue.

Please include the version (`sk64 --version`), your platform, and enough detail to reproduce. You can expect an acknowledgement within a few days. Fixes ship in a patch release with credit unless you prefer otherwise.

## Supported versions

The latest release receives security fixes.

## Known limitations by design

These are properties of what sk64 does, not bugs. They are documented so you can decide whether the tool fits your environment.

### Plaintext secrets touch local disk

Editing a value requires handing it to `$EDITOR`, which means writing it to a file. sk64:

- creates a `0700` per-invocation directory, preferring `/dev/shm`, then `$XDG_RUNTIME_DIR`, then `os.TempDir()`;
- verifies the directory's ownership and mode after creating it (the `0700` directory, rather than file permissions alone, is what prevents both content access and filename enumeration on a shared `/dev/shm`);
- names files after kind/name/key — never after content;
- removes the directory on exit and on SIGINT/SIGTERM/SIGHUP, best-effort zero-overwriting file contents first; while sk64 is blocked waiting for a child editor, cleanup cannot run until that child exits.

The zero-overwrite is symbolic on tmpfs and copy-on-write filesystems. The `0700` directory on tmpfs is the real mitigation.

### Editor artifacts are only mitigated for vim

sk64 passes `-n -i NONE` to `vi`, `vim`, and `nvim`, suppressing swapfiles and viminfo/registers. If you have enabled `set undofile`, vim still writes undo history containing your edit under `~/.local/state`. sk64 does not fight this.

Other editors may write backups, swap files, session state, or crash-recovery data wherever they please. sk64 makes no guarantees about them.

### The database stores metadata, never values

The per-user SQLite database (`${XDG_DATA_HOME:-~/.local/share}/sk64/sk64.db`, mode `0600` in a `0700` directory) persists project names, repository paths, kube contexts, API server URLs, namespaces, resource and workload **names**, and the context/server origins of links. That is mildly sensitive metadata: it can reveal your infrastructure's shape.

It never stores secret values. This is enforced by a test that reflects over the store's exported API and fails if any method can accept value bytes.

### The debug log stores names and sizes, never values

`--debug-log` is opt-in, created `0600`. Its logging API takes kinds, namespaces, names, key names, byte sizes, and errors — there is no method that accepts value bytes, and a reflection test enforces that.

### Not for every environment

If plaintext secret material must never reach local disk, or if resource-name metadata in a local database is unacceptable, sk64 is the wrong tool. Use it knowingly.

## Supply chain

- `go.sum` is committed and treated as a lockfile. The Go checksum database stays enabled; there are no `replace` directives to forks.
- CI runs `go mod verify`, `govulncheck ./...`, and `gosec` (via golangci-lint) on every push.
- Releases are built with `CGO_ENABLED=0`, published with a `checksums.txt`, an SBOM generated by syft, and a keyless cosign signature.
- The optional `helm` and `kustomize` integrations resolve binaries via `exec.LookPath` and invoke them by absolute path with no shell interpretation. Helm uses `helm template` without `--repo` or installation; `kustomize build` may fetch remote bases declared by the scanned repository.
